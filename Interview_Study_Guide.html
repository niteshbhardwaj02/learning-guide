N01
What is Node.js, and which workloads fit it?
FoundationFundamentals
+

Node.js executes JavaScript outside the browser. An event-driven model lets one JavaScript thread per isolate coordinate many waiting I/O operations. This suits APIs, streaming and real-time gateways. CPU-heavy JavaScript still blocks that isolate unless partitioned or moved to workers. Choose it for a workload and team, not because "single-threaded" supposedly means there are no other threads.

Follow the flow

Request → JavaScript handler → asynchronous I/O → completion callback → response

Avoid this trap. Confusing concurrent I/O with parallel execution of JavaScript.
Follow-up to practise aloud: Where would you put image resizing in this architecture?
References: Do not block the event loop or worker pool Node.js worker threads
N02
Explain the event loop without memorizing a misleading ordering rule.
IntermediateFundamentals
+

The event loop runs callbacks in phases, including timers, poll and check; microtask processing happens at defined checkpoints. A timer specifies a minimum threshold, not an exact deadline. Since libuv 1.45 / Node 20, timers run after poll rather than on both sides. Top-level setTimeout(0) versus setImmediate ordering is not a universal guarantee; the scheduling context matters.

Follow the flow

Run callback → process queued microtasks → return to event-loop work

Avoid this trap. Claiming a zero-millisecond timer executes immediately.
Follow-up to practise aloud: How does scheduling inside an I/O callback differ from top-level scheduling?
References: Node.js event loop and nextTick
N03

IntermediateCoding

References: Node.js event loop and nextTick
N04
Does async/await make CPU-bound code non-blocking?
FoundationFundamentals
+

No. An async function executes synchronously until it reaches an await that yields. Wrapping a large loop in an async function or Promise does not move the loop to another thread. Use asynchronous APIs for I/O; for expensive computation, measure first and consider a bounded worker pool, a background service or smaller chunks.

Follow the flow

CPU loop on main isolate → other requests wait; worker pool → main isolate remains available

Avoid this trap. Using Promise.resolve(expensiveCalculation()) as a performance fix.
Follow-up to practise aloud: How would you prove that event-loop blocking is the bottleneck?
References: Do not block the event loop or worker pool
N05
How do Promise.all, allSettled and bounded concurrency differ?
IntermediateCoding
+

Promise.all combines results in input order and rejects when an input rejects; it does not cancel the other work. allSettled reports every outcome. Neither limits how many operations you start. For thousands of calls, use a worker pool or concurrency limiter with deadlines, backpressure and a policy for partial failures. The example starts at most limit operations at once.

Follow the flow

Items → bounded workers → collected outcomes → caller decides partial-failure policy

// Educational utility: records every success/failure in input order.
async function mapLimited(items, limit, fn) {
  if (!Array.isArray(items) || !Number.isInteger(limit) || limit < 1)
    throw new TypeError('Expected an array and positive integer limit');
  let next = 0;
  const out = new Array(items.length);
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, async () => {
    while (next < items.length) {
      const i = next++;
      try { out[i] = { status: 'fulfilled', value: await fn(items[i], i) }; }
      catch (reason) { out[i] = { status: 'rejected', reason }; }
    }
  }));
  return out;
}
Avoid this trap. Launching 100,000 requests before passing their promises to a limiter.
Follow-up to practise aloud: How would you add cancellation after a terminal error?
References: Node.js globals, fetch and AbortSignal AWS bounded retries and jitter
N06
When do you use worker threads, processes or more replicas?
IntermediateFundamentals
+

Worker threads provide parallel JavaScript execution inside a process and can transfer or share memory. Processes provide stronger address-space isolation and can run external programs. Replicas scale independent requests across instances. Use a reusable worker pool for sustained CPU work, rather than creating a thread per small task. Include serialization cost, memory, queue depth and crash behavior in the decision.

Follow the flow

CPU job → bounded queue → available worker → result; HTTP requests → load balancer → replicas

Avoid this trap. Adding workers to ordinary asynchronous database queries without measuring.

References: Node.js worker threads
N07
What are streams and backpressure?
IntermediateFundamentals
+

Streams process chunks instead of buffering the entire payload. Backpressure stops a fast producer from overwhelming a slower consumer. A writable returning false means stop writing until drain; pipeline manages flow and propagates errors across connected streams. Memory can still grow if your own buffers, transformations or queues are unbounded.

Follow the flow

Readable → transform → writable; slow writable signals upstream to slow down

// Save as compress.mjs; run: node compress.mjs input.log output.gz
import { createReadStream, createWriteStream } from 'node:fs';
import { pipeline } from 'node:stream/promises';
import { createGzip } from 'node:zlib';
const [input, output] = process.argv.slice(2);
if (!input || !output || input === output) {
  console.error('Provide distinct input and output paths'); process.exitCode = 1;
} else {
  try { await pipeline(createReadStream(input), createGzip(), createWriteStream(output, { flags: 'wx' })); }
  catch (error) { console.error(error.message); process.exitCode = 1; }
}
Avoid this trap. Ignoring write() returning false.
Follow-up to practise aloud: What would you measure during a 5 GB export?
References: Node.js streams

N10
How do you enforce an outgoing request deadline?
IntermediateCoding
+

Pass an AbortSignal to fetch and set a finite budget. A fetch Promise can fulfill for an HTTP error, so inspect response.ok. Distinguish timeout, cancellation, transport failure and application errors. Aborting a request does not prove that a remote side effect did not occur; a retried write may therefore need an idempotency key.

Follow the flow

Deadline → fetch + signal → status validation → bounded body consumption

// Modern Node.js; bounded time, not an automatic retry policy.
async function readJSON(url, timeoutMs = 2000) {
  if (!Number.isFinite(timeoutMs) || timeoutMs <= 0) throw new RangeError('Invalid timeout');
  const response = await fetch(url, { signal: AbortSignal.timeout(timeoutMs) });
  if (!response.ok) {
    await response.body?.cancel();
    throw new Error(`Upstream HTTP ${response.status}`);
  }
  return response.json(); // Add a body-size limit for untrusted endpoints.
}
Avoid this trap. Using Promise.race only, leaving the underlying network operation running.
Follow-up to practise aloud: How do you divide a 500 ms request budget across dependencies?
References: Node.js globals, fetch and AbortSignal Stripe idempotent requests

Measured pain → explicit boundary → isolated data contract → gradual extraction → evaluate results

Avoid this trap. Decomposing by database table rather than a coherent business capability.
Follow-up to practise aloud: Which extracted service can operate and deploy independently?

Assume answers must cite authorized internal material. Ingest documents through parsing, chunking and a versioned searchable index. At query time authenticate the user, apply document-level permissions during retrieval, select useful context and generate a grounded answer. Treat retrieved text as untrusted data, not instructions. Evaluate retrieval relevance, unsupported claims, permission leaks, latency and cost. Track source versions, support abstention and restrict any tool actions separately.

Documents → permission-aware index; user → authorized retrieval → context → model → cited answer

Avoid this trap. Using a shared semantic cache that returns one user's private context to another.
