01
How should you structure a system-design interview?
FoundationFirst 20Visual flow
+
Core answer

Begin by agreeing on users, the main use cases, and what is out of scope. State measurable targets and assumptions. Estimate the traffic that drives architecture, sketch an API and data model, and draw the simplest complete request path. Deep-dive into the hardest requirement, then test your design against failures, security and cost. Explain why each component exists and which alternative you rejected.

Flow
Requirements → estimates → API and data → architecture → deep dive → failure review
Trade-off / example

A useful practice allocation for a 45-minute session is 5 minutes framing, 5 estimating, 10 sketching, 15 deep-diving and 10 reviewing. This is a suggested exercise, not a hiring-company rule.

Watch out

Do not start with a shopping list of Kafka, Redis, Kubernetes and microservices.

Interviewer follow-up and answer

What should you do when the interviewer changes the scale? Identify which assumption broke, then change the smallest relevant part of the design.

02
Which requirements must you clarify first?
Foundation
+
Core answer

Distinguish functional requirements, such as sending a message, from quality requirements, such as delivering it within a target latency. Ask about active users, peak traffic, object sizes, retention, geography, availability, freshness, privacy and budget. Name invariants: for example, one seat cannot have two confirmed owners. Record assumptions when the interviewer leaves a detail open.

Flow
User goal → acceptance criteria → workload → invariants → explicit exclusions
Trade-off / example

Stronger freshness, lower latency and higher availability can require different mechanisms. Prioritize requirements rather than labeling every one critical.

Watch out

"Highly scalable" is not a measurable requirement.

Interviewer follow-up and answer

What matters most for a payment design? The correctness and recovery of money movement, not merely a low average response time.

03
How do you estimate traffic, storage and bandwidth?
FoundationFirst 20Visual flow
+
Core answer

Use requests per second = daily operations / 86,400, then apply a stated peak multiplier. Compute raw storage as writes per day x bytes per item x retention days, and separately add replicas, indexes, metadata and backups. Estimate bandwidth using bytes transferred per second; distinguish bytes from bits. Quantify read/write ratios and skew because one hot key can dominate a system.

Flow
Users x actions/day → average RPS → peak RPS → bytes/s → retention footprint
Trade-off / example

Illustration: 10 million daily users x 20 reads = 200 million reads/day, about 2,315 average RPS. A hypothetical 5x peak gives about 11,574 RPS. Ten million 500-byte writes/day give 5 GB/day and 150 GB over 30 days, before overhead.

Watch out

Do not multiply read traffic into storage or present invented peak factors as measured facts.

Interviewer follow-up and answer

How much raw storage with three copies? 150 GB x 3 = 450 GB, excluding indexes and backups.

04
How do latency, throughput and concurrency differ?
Foundation
+
Core answer

Latency is the elapsed time for an operation; throughput is completed operations per unit time; concurrency is the number in progress. In a stable system, average in-flight work equals arrival rate times average time in the system. Inspect tail percentiles, queue time and dependency fan-out rather than relying only on averages. State whether you measure server latency or end-to-end user latency.

Flow
Arrival → queue wait → service and dependency work → response
Trade-off / example

Example: 2,000 requests/second x 0.15 seconds average duration = 300 average in-flight requests. Increasing concurrency can improve utilization until a bottleneck saturates, after which queues grow.

Watch out

Do not add component p99 values and call the sum the exact end-to-end p99.

Interviewer follow-up and answer

Why can average latency look healthy while users complain? A slow tail or a specific endpoint can be hidden by aggregate averages.

05
What is the difference between high-level and low-level design?
Foundation
+
Core answer

High-level design describes service boundaries, data ownership, communication, storage, scale and failure domains. Low-level design turns one area into interfaces, classes or modules, state transitions, algorithms and tests. Connect the levels: an idempotent booking API needs a concrete uniqueness constraint, transaction boundary and retry contract, not just an architecture box labeled booking service.

Flow
Business capability → service contract → module interfaces → state transitions → tests
Trade-off / example

At high level, avoid implementing every class. At low level, do not hide correctness behind a distributed-service diagram.

Watch out

An object-oriented class diagram alone does not answer a distributed-system scaling question.

Interviewer follow-up and answer

What carries across both levels? Invariants, ownership, error semantics, concurrency and clear boundaries.

06
When should you scale vertically or horizontally?
Foundation
+
Core answer

Vertical scaling gives a node more resources; horizontal scaling adds nodes. First identify the constrained resource and benchmark. Stateless request handling often scales horizontally more simply than a database with shared writes. Keep spare capacity for failures and account for connection limits, partitioning and coordination overhead. A larger database node can be a sensible intermediate step before sharding.

Flow
Measure bottleneck → improve efficiency → add capacity → load-test → repeat
Trade-off / example

Horizontal scaling adds failure handling and coordination; vertical scaling has machine-size limits and may require a restart. Neither fixes a poorly indexed query automatically.

Watch out

Do not claim doubling servers always doubles throughput.

Interviewer follow-up and answer

What survives one-zone failure in a three-zone deployment? The two remaining zones together must carry the required peak, with appropriate headroom.

07
Should you start with a monolith or microservices?
Foundation
+
Core answer

A modular monolith is a useful starting proposal when one team owns a product with tightly related transactions. Extract services when independent ownership, release cadence, scaling or isolation justify the added network boundary. A microservice should own a coherent capability and its data, rather than merely mirror a database table. Define contracts and operational ownership before extraction.

Flow
Modular application → measured pain point → explicit boundary → selective extraction
Trade-off / example

Independent deployment can help large teams, but introduces partial failures, tracing, API evolution and cross-service consistency work.

Watch out

Microservices are not inherently faster, cheaper or more scalable for every workload.

Interviewer follow-up and answer

Which component might you extract first? A separately scaling asynchronous workload, such as media processing, with a clear contract.

08
What makes a service stateless?
Foundation
+
Core answer

A stateless request handler does not require later requests to reach the same process for correctness. Durable state lives in a database, object store or explicitly managed session store. Local caches and temporary work are still possible if they are disposable. Long-lived connections have connection state, so a real-time gateway also needs reconnect and session-routing behavior.

Flow
Any healthy instance → shared authoritative state → response
Trade-off / example

Externalizing state simplifies replacement and scaling but adds remote dependencies. A signed token reduces session lookups, while revocation and permission changes still need a policy.

Watch out

Stateless does not mean the application has no data or that failover is free.

Interviewer follow-up and answer

What happens if a gateway dies? Clients reconnect, reauthenticate and resume from a durable cursor where applicable.

09
What does CAP actually tell you?
IntermediateFirst 20Visual flow
+
Core answer

During a network partition, a distributed read/write system cannot guarantee both linearizable consistency and a successful response from every non-failed node. Explain the behavior for a particular operation: a minority partition might reject a seat booking to avoid conflicting owners, while a cached product description can be served stale. CAP availability is a formal property, not the same thing as an annual uptime SLO.

Flow
Partition occurs → preserve one-copy semantics OR keep both sides responsive → reconcile as designed
Trade-off / example

The useful interview discussion is which operations can become unavailable or stale, for how long, and how the system recovers. Normal-operation latency trade-offs still matter when no partition exists.

Watch out

"Pick any two forever" is an oversimplification; network partitions are a failure condition to handle.

Interviewer follow-up and answer

Can one product use different choices? Yes. Its inventory reservation and recommendation endpoints can have different consistency contracts.

10
Which consistency model does an application need?
IntermediateFirst 20
+
Core answer

Linearizability makes each operation appear instantaneous in an order that respects completed-before-started operations. Eventual consistency permits temporary divergence with convergence under its assumptions. Read-your-writes is a session guarantee; causal consistency preserves causal relationships. Serializability concerns equivalence to a serial order of transactions and does not, by itself, require real-time order. Choose guarantees per operation and data boundary.

Flow
Business invariant → required observations → consistency guarantee → mechanism
Trade-off / example

Use stronger coordination where stale decisions violate correctness, and weaker guarantees where temporary staleness is acceptable. Document whether guarantees apply to one key, a transaction or multiple regions.

Watch out

Do not use strong consistency, serializability and linearizability as interchangeable labels.

Interviewer follow-up and answer

How can a profile update avoid a stale immediate read? Route the session to an appropriate fresh replica or primary, or use a version-based read barrier.

Make request paths, contracts and boundaries explicit.

11
What happens between entering a URL and receiving a response?
FoundationVisual flow
+
Core answer

At a useful design level, name URL parsing, cache checks, DNS resolution if needed, transport and TLS establishment or reuse, HTTP routing, service execution and the response. An HTTP/3 path uses QUIC rather than a TCP connection. Explain which layers can cache, time out or fail, and where identity and request tracing enter the path.

Flow
Browser → DNS if needed → secure connection → edge/load balancer → service → data
Trade-off / example

Connection reuse and caching avoid repeated work. DNS, certificate handling and connection setup can influence user latency even if application code is fast.

Watch out

Do not assume every request creates a new connection or always reaches the origin.

Interviewer follow-up and answer

Where would you measure latency? At the client or edge for experience, and at internal spans to diagnose the cause.

12
How do load balancers, reverse proxies and API gateways differ?
Foundation
+
Core answer

A load balancer distributes traffic across healthy backends. A reverse proxy receives requests on behalf of services; an API gateway typically adds API policies such as routing, quotas and authentication. These roles can overlap in one product. Layer-4 routing uses transport-level information, while layer-7 routing can inspect HTTP paths and headers. Explain health checks, connection draining and routing algorithms.

Flow
Client → regional entry → policy/routing → healthy backend pool
Trade-off / example

Least-connections or load-aware routing can help uneven requests; affinity simplifies some sessions but makes balancing and failover harder. Replicate the entry layer rather than drawing one literal irreplaceable box.

Watch out

An API gateway does not eliminate authorization checks inside the owning service.

Interviewer follow-up and answer

How do you deploy without dropping work? Stop new routing to retiring instances, drain existing connections and enforce a bounded deadline.

13
What should you cache at a CDN or edge?
Foundation
+
Core answer

Cache public, reusable representations near users, with explicit freshness and validation rules. Use versioned asset names for immutable files and carefully designed cache keys for variable responses. Separate shared caches from user-private caching. A response containing personalized or authorization-sensitive data must not accidentally share a cache entry across identities or tenants.

Flow
Client → nearest cache → hit: response; miss: origin → cache according to policy
Trade-off / example

Long freshness reduces origin work but delays changes. Revalidation and versioned URLs can balance bandwidth and freshness; invalidation must be designed, not assumed instantaneous everywhere.

Watch out

Cache-Control: no-cache means revalidate before reuse, not "never store"; no-store prohibits storage.

Interviewer follow-up and answer

Why include relevant request variation in the key? Otherwise different representations can collide and users receive the wrong content.

14
How do you choose REST, gRPC or GraphQL?
Intermediate
+
Core answer

Choose by clients and access patterns. A resource-oriented HTTP API is often straightforward for public integrations. gRPC offers typed service contracts and streaming mechanisms for suitable clients. A graph query layer can let clients request related fields, but needs query-cost controls and careful resolver behavior. State the versioning, authentication, cancellation and error contract regardless of protocol.

Flow
Client needs → contract style → transport constraints → operational controls
Trade-off / example

Typed internal calls can reduce ambiguity, while browser and partner compatibility may favor HTTP/JSON. More flexible queries shift work toward cost estimation, caching and authorization.

Watch out

Do not claim one protocol is universally faster; payloads, serialization, batching and workload shape determine results.

Interviewer follow-up and answer

How do you prevent excessive graph-query work? Bound query depth, complexity, result sizes and per-identity resource consumption.

15
When should you use polling, SSE or WebSockets?
Foundation
+
Core answer

Polling fits infrequent updates and simple clients. Server-sent events, or SSE, carry server-to-client events over an HTTP response; clients can send commands separately. WebSockets support bidirectional communication and fit interactive exchanges. None of these transports automatically provides durable message history, exactly-once business processing or replay. Add event IDs, heartbeats, bounded buffers and reconnect behavior.

Flow
Low update rate: poll | one-way live stream: SSE | bidirectional session: WebSocket
Trade-off / example

Long-lived connections need gateway capacity and lifecycle management. Simpler polling can be sufficient when a few seconds of delay is acceptable.

Watch out

Choosing WebSockets alone does not solve offline delivery or message ordering across reconnects.

Interviewer follow-up and answer

What suits streamed assistant tokens? SSE is a reasonable proposal for one-way output; choose another transport when the interaction requires it.

16
How do you make a create or payment API idempotent?
IntermediateFirst 20Visual flow
+
Core answer

Accept a client-generated key scoped to the caller and operation. Atomically record the key, request fingerprint and business outcome, with a uniqueness constraint protecting concurrent retries. Return the prior outcome for matching retries and reject a reused key with different parameters. Define pending behavior and a retention period. For external side effects, propagate a stable key or reconcile with the provider.

Flow
Request + key → atomic claim → perform/record outcome → same retry returns same outcome
Trade-off / example

The key must represent one logical intent, not every similar-looking request. Retention costs storage; expiry means the duplicate-protection window is bounded.

Watch out

A cache lookup followed by an unprotected database write leaves a race and is not sufficient.

Interviewer follow-up and answer

What if the first response is lost? The client retries the same logical operation with the same key, then checks its durable status.

17
How do you design reliable pagination?
Intermediate
+
Core answer

For a changing feed, propose keyset pagination using a stable sort such as (created_at, id), with a cursor describing the last position and filters. Query after that tuple with an appropriate index. Offset pagination is simple and supports jumping to a numbered page, but deep offsets and concurrent inserts can cause poor behavior. Specify snapshot expectations and tie handling.

Flow
First page → stable last-item cursor → next page using indexed boundary
Trade-off / example

Keyset pagination trades arbitrary page jumps for stable traversal. For a consistent export, use a snapshot or fixed upper boundary rather than a live feed contract.

Watch out

Encoding an offset in Base64 does not turn it into keyset pagination.

Interviewer follow-up and answer

Why include a unique tie-breaker? Multiple records can have the same timestamp, so timestamp alone can skip or repeat rows.

18
How would you design a distributed rate limiter?
IntermediateFirst 20Visual flow
+
Core answer

Choose the scope: user, API key, tenant, endpoint or IP, with global safeguards. A token bucket allows a bounded burst while refilling at a sustained rate. Perform refill and consume atomically for a shared bucket. At larger scale, lease quota to regional or local limiters and explicitly accept bounded overshoot, or coordinate centrally when the cap must be strict.

Flow
Request identity → policy lookup → atomic quota decision → allow or throttle
Trade-off / example

Central checks simplify a strict limit but add latency and a dependency. Local quotas improve availability but can waste capacity or allow bounded divergence.

Watch out

An IP-only limit can punish many users behind one network and does not establish identity.

Interviewer follow-up and answer

How do you handle limiter failure? Choose fail-open or fail-closed by endpoint risk, with a conservative local emergency limit.

19
How do APIs evolve without breaking clients?
Intermediate
+
Core answer

Prefer backward-compatible additions, stable field meanings and documented defaults. Introduce a new version for incompatible behavior, with telemetry for usage and a retirement plan. For rolling deployments, old and new clients and servers may coexist. Validate contracts automatically and keep event schemas independently versioned. Treat changes to errors, ordering and pagination as contract changes too.

Flow
Add compatible capability → deploy readers → deploy writers → migrate clients → retire old behavior
Trade-off / example

Long compatibility windows reduce client disruption but increase maintenance. Decide who owns migration and how unsupported clients fail.

Watch out

Renaming a field is not harmless just because the JSON remains syntactically valid.

Interviewer follow-up and answer

What about database changes? Use expand-and-contract so both application versions can operate during the migration.

20
How do you deliver and receive webhooks safely?
Intermediate
+
Core answer

Treat delivery as retryable and potentially duplicated or out of order. Sign the payload, verify the raw request body and timestamp according to the provider contract, and persist an inbox record before acknowledging accepted work. Process asynchronously with deduplication and bounded retries. For outbound delivery, keep a durable event and attempt history, and protect URL fetching against unsafe destinations.

Flow
Event → durable delivery job → signed POST → durable receiver inbox → asynchronous processing
Trade-off / example

Fast acknowledgment reduces timeout retries but means acceptance and completion are different states. Define replay windows, subscription ownership and secret rotation.

Watch out

Do not assume webhook arrival order matches event creation order or that one successful HTTP response proves business completion.

Interviewer follow-up and answer

What if an event arrives twice? The receiver atomically recognizes its event ID and avoids repeating the side effect.

21
How do you choose SQL versus NoSQL?
FoundationFirst 20
+
Core answer

Start with access patterns, invariants, relationships, transaction scope, expected scale and operational skill. A relational database is a useful default proposal when joins and constraints matter. Key-value, document, wide-column and graph databases optimize different data shapes and queries; "NoSQL" is not one consistency or transaction model. Validate the specific product and configuration instead of relying on labels.

Flow
Queries + invariants → data model → required guarantees → candidate store → benchmark
Trade-off / example

Denormalization can make reads simpler while duplicating data and complicating updates. Multiple specialized stores can help, but each adds synchronization and recovery work.

Watch out

SQL does not mean unscalable, and NoSQL does not mean no transactions.

Interviewer follow-up and answer

When would a key-value store fit? Known-key lookups with a well-distributed partition key and limited relational query needs.

22
How do indexes work, and when do they hurt?
Foundation
+
Core answer

An index provides an alternative access path so the database can locate matching records without scanning all data. Design it around filters, joins and ordering, then inspect actual query plans. Composite-column order matters; covering or partial indexes can help particular workloads. Every additional index consumes space and introduces maintenance work when indexed data changes.

Flow
Query shape → candidate index → plan inspection → representative benchmark
Trade-off / example

An index that helps a frequent read may slow writes or increase memory pressure. Index usefulness depends on selectivity, query form and the optimizer.

Watch out

Do not create an index on every column or assume the optimizer always chooses the one you expect.

Interviewer follow-up and answer

What index might suit a tenant feed? A composite index beginning with tenant_id and followed by the chosen sort keys.

23
What is the difference between partitioning and sharding?
IntermediateFirst 20Visual flow
+
Core answer

Partitioning divides data into pieces, for example by range, list or hash. Sharding distributes those pieces across independently managed database nodes or groups. Choose keys that support the dominant queries and distribute load; plan metadata routing, rebalancing and cross-shard operations. A database table partitioned within one server is not automatically a horizontally sharded database.

Flow
Record key → partition/shard router → owning data partition
Trade-off / example

Tenant-based sharding localizes tenant queries but can create oversized tenants. Time ranges simplify retention but may concentrate new writes on the newest range.

Watch out

A high-cardinality key can still be hot when access is heavily skewed.

Interviewer follow-up and answer

How do you move a shard safely? Copy a snapshot, catch up changes, fence or coordinate writes, switch routing and verify before retiring the old owner.

24
How do replication and read replicas affect correctness?
IntermediateFirst 20
+
Core answer

Replication keeps copies for resilience or read capacity. With asynchronous replication, a replica can lag behind acknowledged primary writes. Synchronous replication trades additional coordination for a stronger acknowledgment contract, whose exact durability depends on the configured acknowledgment stage and failure model. Plan promotion, old-primary fencing and how clients discover the new owner.

Flow
Write → primary → replication → replicas; read route depends on freshness contract
Trade-off / example

Read replicas offload suitable reads but do not automatically add primary write throughput. A fresh read may need the primary or a replica caught up to a known position.

Watch out

Do not promise zero data loss from an asynchronously replicated failover.

Interviewer follow-up and answer

How do you handle read-after-write? Use a session barrier, route to the primary, or wait for the relevant replica position.

25
Does R + W > N guarantee strong consistency?
Advanced
+
Core answer

For a fixed replica set of size N, read and write sets of sizes R and W must intersect when R + W > N. That arithmetic alone does not prove linearizability. You must still specify version selection, concurrent-write resolution, membership changes, failed writes, sloppy quorums and the read/write protocol. Majority-based systems need a correct coordination protocol, not merely a quorum count.

Flow
Write acknowledgments → intersecting read set → version/protocol rules → selected value
Trade-off / example

For N = 3, R = 2 and W = 2 force an intersection. A larger quorum can reduce availability under failures and increase latency.

Watch out

An intersecting quorum is not a complete consistency proof.

Interviewer follow-up and answer

How would you defend a strong-consistency claim? Name the actual protocol and the assumptions under which its read and commit rules hold.

What are ACID and transaction isolation?
IntermediateFirst 20
+
Core answer

Atomicity makes a transaction all-or-nothing; consistency means preserving defined database invariants; isolation constrains concurrent observations; durability concerns committed data surviving specified failures. Isolation levels admit different anomalies. Serializable execution is equivalent to some serial order, but applications must handle aborted transactions. Product-specific behavior matters: PostgreSQL repeatable read uses snapshot isolation and can still admit serialization anomalies.

Flow
Begin → read/check → write → commit OR rollback/retry
Trade-off / example

Stronger isolation may add coordination or retries. For a small invariant, a constraint or atomic conditional write may be clearer than a long multi-step transaction.

Watch out

ACID consistency is not the same definition as the C in CAP.

Interviewer follow-up and answer

What is write skew? Concurrent transactions each read a condition, update different records and together violate an invariant.

27
How do you prevent overselling or double booking?
IntermediateFirst 20
+
Core answer

Place the invariant in the authoritative store. For stock, an atomic conditional update such as "decrement if available >= requested" avoids a separate unprotected check and write. For a seat, enforce one current owner with a unique constraint or serialized reservation transition. Keep the booking state and inventory mutation in the same local transaction when possible, and make client retries idempotent.

Flow
Request → atomic reserve → persist reservation → commit → confirmation
Trade-off / example

Pessimistic locking queues contenders; optimistic version checks make losers retry. Choose based on contention and business semantics.

Watch out

A cache check or a distributed lock alone is not a substitute for a durable correctness constraint.

Interviewer follow-up and answer

What if payment completes after a hold expires? Re-check the reservation version/state and follow an explicit refund or manual-reconciliation policy.

28
How do cache-aside, write-through and write-behind differ?
IntermediateFirst 20Visual flow
+
Core answer

In cache-aside, the application checks the cache and loads missing data from the authoritative store. On writes, it commonly commits to the store and invalidates or updates the cache. Write-through updates through a caching layer that also writes the backing store. Write-behind delays backing-store persistence, so failures can lose acknowledged changes unless the buffering path is durably protected.

Flow
Read → cache hit: return; miss: database → populate cache → return
Trade-off / example

Cache-aside is flexible but permits races and stale data. Time-to-live bounds age only under stated update/refresh behavior; version checks or coordinated invalidation are needed for stricter guarantees.

Watch out

Invalidating after a write does not remove every stale-refill race.

Interviewer follow-up and answer

Where is write-behind risky? Authoritative financial or inventory changes when cache loss would violate the durability contract.

29
How do you handle cache stampedes, hot keys and penetration?
Intermediate
+
Core answer

For a hot expired key, collapse concurrent loads so one refresh performs the database work. Spread expirations with jitter, prewarm predictable hot data and consider serving bounded-stale values during refresh where safe. Cache legitimate negative results briefly to avoid repeated misses, while bounding attacker-controlled key growth. Hot-key replication or local caches can reduce shared-cache contention.

Flow
Many misses → one refresh owner → database → cache fill → waiting readers resume
Trade-off / example

Stale-while-revalidate protects latency but trades freshness. A local cache multiplies invalidation surfaces and memory usage.

Watch out

Increasing total cache capacity does not necessarily fix one overloaded key.

Interviewer follow-up and answer

How would you protect the database during a cache outage? Limit miss concurrency, shed nonessential reads and keep a controlled fallback budget.

30
How should you generate globally unique IDs?
Intermediate
+
Core answer

Choose by uniqueness, sortability, size, privacy and coordination needs. Random UUIDs reduce central coordination; UUIDv7 includes a millisecond timestamp field and random or monotonicity-related bits. Sequence-based and timestamp-worker-counter designs require careful allocation and clock behavior. Keep uniqueness constraints at durable write boundaries, and never treat an unguessable-looking identifier as authorization.

Flow
Generation policy → collision/clock handling → durable uniqueness check → expose ID
Trade-off / example

Time-oriented IDs can improve locality but may reveal approximate creation time. Sortability is not a guarantee of global causal order.

Watch out

A timestamp alone is not unique; different nodes can create records in the same tick.

Interviewer follow-up and answer

What happens when a worker clock moves backward? Follow an explicit wait, logical-counter or fail-safe policy rather than silently reusing IDs.

31
How do you store and upload large files?
IntermediateVisual flow
+
Core answer

Keep binary objects in object storage and metadata, ownership and lifecycle state in a queryable database. Authorize an upload, issue a short-lived scoped upload capability, and let the client transfer bytes directly. Verify completion, size and checksum where supported; scan or quarantine untrusted content before publishing it. Use resumable or multipart transfers for large objects.

Flow
